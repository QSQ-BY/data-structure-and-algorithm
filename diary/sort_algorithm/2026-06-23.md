# 2026-06-23：希尔排序，不只看增量序列

今天继续写排序算法，重点放在希尔排序。

前两天刚写完无监督插入排序，今天把这个想法搬到了希尔排序里。普通插入排序处理的是一整段连续区间，希尔排序则先选一个 `step`，把数组拆成若干个间隔为 `step` 的子序列。每个子序列内部做一次插入排序，等 `step` 一轮轮缩小到 1，最后整个数组就会变成有序。

这个思路听起来简单，真正写的时候还是会被下标绕一下。`unsupervised_insert_sort` 多了一个 `step` 参数以后，`i += step`、`j -= step` 才是当前子序列里的前进和后退。外层的 `for(int i = l; i < l + step; i++)` 负责枚举每个子序列的起点。也就是说，`step` 不只是一个距离，它还决定了这一趟到底分成几组。

普通的二分增量版本比较直接：先按较大的 `step` 让远距离元素粗略归位，再逐步缩小 `step`，最后用 `step = 1` 收尾，相当于在一个已经比较接近有序的数组上做插入排序。这里我真正要理解的不是某一行代码，而是每一趟结束后数组状态变得更“接近有序”。

## Hibbard 增量没有想象中快

后面我又写了 `shell_sort_hibbard`，用的是 `2^k - 1` 这一组增量。按理论印象，Hibbard 增量一般应该比单纯的 `n/2, n/4, ...` 更好一些。可实际跑起来，第二种方式反而慢，这一点挺反直觉。

后面问了AI之后我想清楚了，问题不完全出在 Hibbard 序列本身，而是出在我当前搭配的内部排序方式上。

现在每个 gap 子序列都调用无监督插入排序。这个函数会先扫一遍当前子序列，找到最小值，再用相邻交换把它挪到最前面当哨兵。这样后面的内层循环可以少判断边界，但前面多了一次扫描和一串交换。普通插入排序里，这个优化的成本还比较容易接受；放进希尔排序以后，每一趟 gap 都要对很多个子序列重复做这件事，额外开销就被放大了。

Hibbard 的 gap 往往比 `n/2` 那组更小，比如同样在大数组上，第一趟可能是 `4194303`，而不是 `5000000`。gap 更小意味着每个子序列更长，插入排序内部可能移动更多元素。理论上它希望通过更细的预排序减少后面的工作量，但我这里用的是反复 `swap` 的写法，一次交换背后有多次赋值和内存写入，前面的成本很容易把后面的收益抵掉。

今天这个对比让我又回到前几天插入排序和选择排序的那个结论：复杂度和实际耗时不是一回事。希尔排序看起来是在比较 gap 序列，可真正跑起来时，子序列内部到底是交换式插入、搬移式插入，还是带哨兵的版本，都会影响结果。
