# 2026-06-20：重写生日礼物，再看插入排序的效率

今天又全程跟着老师把 HZOJ 289 生日礼物写了一遍。昨天已经把这道题的思路梳理得很细了，所以今天不想再把“压缩正负段、每次删最小代价”重新讲一遍。更值得记下来的，是同一套想法换成老师的代码后，为什么会显得更干净。

## 老师的版本简洁在哪里

最明显的一点是压缩过程。昨天我的写法先读完整个原数组，再把连续正数段和负数段压到一个 `vector` 里，后面还要用 `clean` 把 0 去掉、把可能相邻的同号段重新合并，最后再复制到从 1 开始的 `array` 里。这个流程能工作，但中间状态太多了：`__arr`、`arr`、`clean`、`array`，每换一次名字，我就要在脑子里重新确认它到底代表原序列、压缩序列，还是为了链表准备的序列。

老师的写法是在读入时就完成压缩：

```cpp
int k = 1;
cin >> arr[1];
for(int i = 1; i < n; i++){
    int number;
    scanf("%d", &number);
    if(arr[k] * number < 0){
        k++;
        arr[k] = number;
    }else{
        arr[k] += number;
    }
}
```

`k` 永远指向当前压缩段。新读进来的数如果和当前段异号，就开一个新段；否则直接并到当前段里。这样读完输入之后，`arr[1..k]` 已经是后面真正要处理的序列。没有额外的清洗数组，也没有从 0 下标转到 1 下标的那一层搬运，代码短了一截，更重要的是少了很多“我现在到底在哪个版本的数组里”的疑问。

第二个优化是状态更集中。老师直接用 `MAX_N` 开了 `arr`、`l`、`r` 这几个数组，压缩后的段、左邻居、右邻居都落在同一套下标上。初始化时顺手完成三件事：统计正数段个数 `cnt`，累加正数段总和 `sum`，把每一段按绝对值放进 `set`，同时接好模拟链表。

```cpp
for(int i = 1; i <= n; i++){
    if(arr[i] > 0){
        cnt++;
        sum += arr[i];
    }
    s.insert(PII(abs(arr[i]), i));
    l[i] = i - 1;
    r[i] = i + 1;
}
```

我昨天的代码也做了这些事，但分散在不同位置。看起来每一步都很清楚，合起来却会拖长阅读距离。老师的版本把“这个点的值、这个点在集合里的代价、这个点在链表里的位置”放在同一轮循环里建立起来，读代码的时候更容易相信这些状态是一组东西。

合并段的时候也是同样的感觉。选出绝对值最小的段以后，老师先拿到 `index`、`left`、`right`，再判断这个点能不能删或合并。只要执行这次操作，就立刻更新 `sum` 和 `cnt`，再把左右两边并到 `arr[index]`，同时摘掉链表节点、打删除标记。修改相邻关系的代码贴在合并值的旁边，含义比较顺。

这让我意识到，代码“美观简洁”不是单纯少写几行，而是让同一件事的状态尽量靠在一起。生日礼物这题本来就要同时维护 `set`、模拟链表、删除标记和答案，如果代码还把这些状态拆得很散，后面调试时就会变成到处找线头。老师的版本没有换算法，只是把状态摆放得更稳。

## 插入排序：理论次数和实际耗时不是一回事

后面又写了插入排序。算法本身不难：从第二个位置开始，把当前元素一路往前比较，只要它比前一个小，就和前一个交换，直到它落到已经有序的前缀里。每一轮结束后，左边那一段都保持有序。

```cpp
void insert_sort(int* arr, int l, int r){
    for(int i = l + 1; i < r; i++){
        int j = i;
        while(j > l and arr[j] < arr[j - 1]){
            swap(&arr[j], &arr[j - 1]);
            j--;
        }
    }
}
```

刚写完的时候，我对插入排序的预期其实挺高。选择排序每一轮都要把待排序区完整扫一遍，不管数据原来有没有接近有序，比较次数都很固定。插入排序至少可以提前停下来，理论上执行次数大概只有选择排序的一半；如果数组本来就比较有序，它甚至会轻很多。

但实际测试里，插入排序的耗时反而比选择排序更长。这个结果一开始有点反直觉，后来听完老师的讲解后我想明白了：选择排序反复做的是比较，只有每轮最后才交换一次；插入排序在当前写法里反复做的是相邻交换。一次 `swap` 不是一个轻飘飘的动作，它里面有三次赋值，还会带来更多内存写入。随机数据里逆序对很多，插入排序每遇到一个逆序关系就要把元素往前挪一步，循环次数虽然可能少一些，但每次循环付出的代价更重。

这件事把“时间复杂度”和“实际运行效率”之间的距离摊开了。复杂度看的是增长趋势，但程序真的跑起来时，比较、交换、赋值、内存访问并不是同一种成本。选择排序看起来笨，因为比较次数多；插入排序看起来聪明，因为能提前停止。可如果插入排序用相邻交换来搬元素，实际开销就会被交换次数拖住。

今天这个观察对我挺有用。以前我看 `O(n^2)` 算法时，容易只停留在一个大概印象：都是平方级，谁好谁坏看次数。现在更能感觉到，分析算法效率不能只数循环，还要看循环里到底干了什么。
