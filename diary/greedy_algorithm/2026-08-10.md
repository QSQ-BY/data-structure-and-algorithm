# 2026-08-10：从熟悉的前缀和，到需要证明的贪心选择

今天照常完成了两道洛谷日练，也正式开始主线里的贪心算法。两部分放在一起看，差别很明显：前缀和的题已经能顺着熟悉的公式往下推，递归题则提醒我，照着定义写出函数不等于把题做完；到了贪心，最大的困难又往前挪了一步，常常不是代码怎么写，而是先找到那个局部选择，再说明它为什么不会让全局答案变差。

## K 倍区间：熟悉的前缀和与余数

今天第一道日练是 K 倍区间。它和之前做过的余数类前缀和很接近：设前缀和为 `prefix[i]`，区间 `[l,r]` 的和是 `prefix[r]-prefix[l-1]`。如果这两个前缀和除以 `k` 的余数相同，它们的差就一定是 `k` 的倍数。

```cpp
for(long long  i=0;i<n+1;i++){
    prefix[i] = prefix[i]%k;
    h[prefix[i]]++;
}
long long  ans = 0;
for(auto x:h){
    long long  number = x.second;
    if(number>1){
        ans +=f(number);
    }
}
```

这里把 `prefix[0]` 也放进统计，才能覆盖从第一个数开始的区间。同一种余数出现 `number` 次，任取两个前缀位置就能得到一个 K 倍区间，因此贡献是组合数 `number*(number-1)/2`。整道题只需要线性扫描，再统计每种余数出现的次数，平均时间复杂度是 `O(n)`。

这道题不难，更多是在维持日常练习的手感。现在看到“区间和能否整除某个数”，我已经会自然地把问题改写成“两个前缀和的余数是否相同”，不用再从每个区间本身出发枚举。

## 递归函数：把定义写出来以后，计算才刚开始

另一道日练是递归函数设计。题面把不同条件下的递推式写得很完整，我一开始以为只要照葫芦画瓢，把几个分支翻译成递归调用就行。结果提交后严重超时，这才发现，同一个 `(a,b,c)` 会从许多不同路径反复到达。公式虽然写对了，计算过程却做了大量重复工作。

解决办法是给每个状态保存一次计算结果。再次遇到相同的 `(a,b,c)` 时直接读取，不再展开整棵递归树。由于超过 `20` 的参数都会转到 `w(20,20,20)`，真正需要记录的状态数量很小，用一个三维数组就能覆盖。

这个思路和我在 DFS 中接触过的剪枝很像，目的都是避免继续走没有必要的计算。不过更准确地说，这里用的是记忆化搜索：剪枝通常是在确认某条分支不可能产生更好答案后停止，记忆化则是认出“这个状态以前算过”，直接复用结果。今天这道题让我重新意识到，递归函数的定义只描述答案之间的关系，程序是否跑得动，还要看状态会不会被重复访问。

## 最大整数：不维护答案，只比较相对顺序

贪心主线的第一道题要求把多个整数拼成最大的数。它和以前做过的国王游戏有一点相似：最后都要借助排序，把一个看起来需要尝试很多排列的问题，压缩成元素之间的相对顺序。

我最初想维护一个不断增长的 `ans`，遍历到新数字 `a` 时比较 `ans+a` 和 `a+ans`。但这样既把判断绑在了当前答案上，又会很快遇到大整数范围的问题。真正需要回答的其实只是：对于任意两个字符串 `a`、`b`，究竟应该让谁排在前面。

```cpp
bool cmp(string a,string b){
    return stoll(a+b)> stoll(b+a);
}

sort(nums.begin(),nums.end(),cmp);
for(int i=0;i<n;i++){
    cout<<nums[i];
}
```

判断规则是比较 `a+b` 与 `b+a`。如果前者更大，就让 `a` 排在 `b` 前面，排序完成后直接依次输出。当前代码已经把问题缩到了这个相对关系上，但 `stoll` 仍然会在两个十位整数拼接时溢出；两个拼接结果长度相同，实际不需要转换为整数，直接比较字符串就够了。

这道题给我的提醒比那个溢出本身更重要：排序贪心不是先做出一部分完整答案，再拿下一个元素试着拼，而是先定义好任意两个元素之间谁应该在前。只要这个比较关系成立，`sort` 会替我完成剩下的全局排列。

## 删除数字和独木舟：策略不长，难的是为什么

后两道题没有第一题那么直观。删除数字要求删掉固定数量的数位，让剩余数字最小。每次应该删除从左向右遇到的第一个下降位置，也就是在 `number[j]>number[j+1]` 时删掉 `number[j]`；如果整个数字单调不降，就删除最后一位。原因在于结果长度固定，越靠前的数位影响越大。先让前面的数字变小，比保留一个较大的高位、再去优化后面更划算。

独木舟则先把所有人体重排序，每次处理最重的人：如果他连最轻的人都无法同船，其他人更不可能与他搭配，他只能单独出发；如果两人的重量和不超过载重，就把最轻者和最重者配在一起。

```cpp
int min_weight = weight[0];
int max_weight = weight[weight.size()-1];
if(min_weight + max_weight > m){
    weight.erase(weight.begin() + weight.size() - 1);
}else if(min_weight + max_weight <= m){
    weight.erase(weight.begin()+ weight.size()-1);
    weight.erase(weight.begin());
}
ans++;
```

我后来追问了一次：如果某个最优方案里最重者原本和 `x` 同船，最轻者和 `y` 同船，把最重者与最轻者配到一起以后，`x` 和 `y` 凭什么还能同船？关键条件是最重者记为 `H` 时，原方案已经保证 `H+x` 不超过载重，而且 `y<=H`，所以 `x+y<=x+H`，交换搭档不会超载。这个不等式补上以后，“最轻配最重”才不只是感觉合理，而是有了交换依据。

当前实现通过不断删除 `vector` 两端模拟安排过程，思路能表达出来，但删除开头元素会反复搬移后面的数据。更合适的写法是保留排序结果，用左右两个下标向中间移动，把排序后的扫描保持在 `O(n)`；总复杂度由排序决定，为 `O(n log n)`。

## 今天真正开始接触贪心

今天三道贪心题的代码都不长，确定策略的过程却比敲代码慢得多。最大整数要把“当前答案”换成两两顺序；删除数字要注意高位对数值的支配；独木舟还要用交换说明局部配对不会破坏最优方案。它们没有一份可以直接照搬的统一模板，至少我现在还做不到看到题面就立刻抓住选择规则。

以后想到一个贪心策略时，我准备先看看它是不是在处理当前最难安排的对象，以及跳过这一步会留下什么；如果还是没有把握，就拿一个任意的最优方案试着交换，看看能否在不增加代价的前提下换成我的选择。数学直觉暂时不可能一下变强。下一道题开始，我想先把局部选择和理由各写成一句话，再动手写循环。
