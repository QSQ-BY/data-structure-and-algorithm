# 2026-08-04：map 理顺以后，哈希查找也顺了

今天的代码量不算多，洛谷还是保持两道题，难度也都不大。比题量更明显的是，系统学完 `map` 的基本用法以后，我再看哈希查找题时顺了很多。以前只是模糊地知道“查询多就用哈希表”，现在会先想清楚：拿什么当键，需要保存什么值，查询之后还要不要修改或删除。

我先整理了 `map` 的声明、插入、访问、查找、删除和遍历。`map` 与 `unordered_map` 都保存键值对，但前者基于红黑树，键会保持有序，常见操作是 `O(log n)`；后者基于哈希表，不维护顺序，查找平均是 `O(1)`。两者的接口很接近，真正需要判断的是题目究竟更需要顺序，还是更看重直接按键查找。

## P5266：姓名就是最自然的键

P5266「学籍管理」要求维护姓名和成绩之间的对应关系。读完操作以后，映射关系几乎已经写在题面里：姓名作为键，成绩作为值。插入和修改可以统一写成一次下标赋值，查询与删除则先用 `find` 判断姓名是否存在。

```cpp
unordered_map<string,int> h;
// ...
h[name] = score;

if(h.find(name) == h.end()){
    cout<<"Not found"<<endl;
}else{
    cout<<h[name]<<endl;
}

h.erase(name);
```

这道题让我把几种操作连成了一套完整流程。`h[name] = score` 既能插入新学生，也能修改已有成绩；`find` 只负责确认键是否存在，不会像直接使用下标那样意外创建新元素；`erase` 则按照姓名删除整条记录。每一次操作都围绕同一个键进行，用 `unordered_map` 表达很直接，平均复杂度也是 `O(1)`。

## P5250：查找不只有“存在或不存在”

P5250「木材仓库」维护的是互不相同的木材长度。我用 `unordered_set` 保存当前库存：进货时先判重，出货时则寻找与目标长度最接近的木材。如果距离相同，还要选择更短的那根。

```cpp
int temp = INT_MAX;
int ans = INT_MAX;
for(auto x:h){
    if(abs(x-length) < temp){
        temp = abs(x-length);
        ans = x;
    }else if(abs(x-length) == temp){
        ans = min(ans,x);
    }
}
h.erase(ans);
cout<<ans<<endl;
```

这里的哈希集合只保存键，不需要额外的值。遍历时，`temp` 记录目前最小的距离，`ans` 记录对应长度；出现更近的木材就同时更新，距离相同则保留较短值。它和学籍管理的精确查找不同，但思考入口仍然一样：先确定需要维护的数据，再决定容器中应该保存键值对，还是只保存不重复的键。

## 两道题不多，但这一遍很值

今天依然只做了两道洛谷题，写出的代码也不长，两道题最后都顺利通过。不过我并不觉得内容少。前几天做哈希题时，我更多是在记 `unordered_map` 能够加快查询；今天系统看过 `map` 的接口和底层区别以后，我开始能从“数据之间是什么关系”出发选择容器。

以后再遇到查找题，我想先分清三件事：是按键精确查询，还是需要统计次数；数据是否要求保持顺序；查询以后是否还要频繁修改和删除。把这些问题想明白，`map`、`unordered_map`、`set` 和 `unordered_set` 就不再只是几个容易混在一起的 STL 名字，而是各有适用位置的工具。
