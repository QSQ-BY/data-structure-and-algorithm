## 系统栈模拟：把递归过程翻译成状态

老师一共讲了两种递归转非递归的方法。第一种是系统栈模拟法，例子从阶乘开始，随后扩展到二叉树中序遍历和快速排序。

刚接触 `scode` 时，我觉得这种写法很抽象。递归版本明明只有几行，转成非递归以后，却要把参数、局部变量、返回值和执行位置全部装进一份 `Data`。写到后面才发现，它其实很有套路：每一份 `Data` 就是一层函数调用，`scode` 则相当于这一层函数执行到了哪一行。

阶乘中的栈帧把返回值传递也明确保存了下来：

```cpp
class Data{
public:
    Data(int n,int* pre_ret){
        this->n = n;
        this->pre_ret = pre_ret;
        scode = 0;
    }
    int n;
    int ret;
    int* pre_ret;
    int scode;
};

// ...

case 1:{
    Data new_data(cur_data.n-1,&(cur_data.ret));
    s.push(new_data);
    cur_data.scode = 2;
};break;
case 2:{
    *(cur_data.pre_ret) = cur_data.n*cur_data.ret;
    s.pop();
};break;
```

原递归函数准备调用下一层时，就创建一份新的 `Data` 压栈，同时把当前层的 `scode` 移到“等待子调用返回”的状态。子调用结束时弹栈，并通过 `pre_ret` 把结果写入上一层的 `ret`。边界判断、本层操作、递归调用和函数返回被拆成几个分支，再由状态码重新串起来。

中序遍历没有返回值，`Data` 只需要保存当前节点和状态码；快速排序则要额外保存左右边界、扫描下标和基准值。三个例子写完以后，我对这套方法的感觉从“很抽象”变成了“翻译题”：先把递归函数切成若干操作，再把原本由系统维护的调用现场显式放进栈里。

## 拓扑顺序：先处理依赖，再回到当前层

第二种方法借用了图论中的拓扑排序。递归调用可以展开成一张依赖图：当前任务依赖子任务的结果，所以要先处理子任务，再回到当前任务。这个方向比系统栈模拟更形象，但真正写成代码时反而更难，因为调用关系、执行顺序和中间结果都要自己组织。

归并排序的非递归版本先收集所有区间任务，再从后往前执行合并：

```cpp
void non_merge_sort(int* arr,int l,int r){
    Data init_data(l,r);
    vector<Data> datas;
    datas.push_back(init_data);
    for(int i=0;i<datas.size();i++){
        int mid = (datas[i].l+datas[i].r)/2;
        if(mid-datas[i].l>=2){
            Data new_data(datas[i].l,mid);
            datas.push_back(new_data);
        }
        if(datas[i].r-mid>=2){
            Data new_data(mid,datas[i].r);
            datas.push_back(new_data);
        }
    }
    for(int i=datas.size()-1;i>=0;i--){
        merge_sort_once(arr,datas[i].l,datas[i].r);
    }
    return;
}
```

区间在展开时是父任务在前、子任务在后，逆序处理后就变成子区间先完成、父区间再合并，正好符合递归归并排序的依赖关系。除了归并排序，我还写了普通拓扑排序和旅行计划：前者按入度确定线性处理顺序，后者在拓扑序上继续维护到达每座城市的最长路径。

两种方法放在一起看很有意思。系统栈模拟法理解起来绕一些，实现时却能按固定步骤翻译；拓扑方法的图像很清楚，落到代码里却需要先把依赖关系理顺。今天把这一章一口气写完后，明天就要进入“森林与并查集”。这个衔接来得很巧，因为今天比赛里没做出来的 C，恰好也把我引到了连通性上。

## 第一次参加 Codeforces Round 1109（Div. 3）

今天也算正式向算法竞赛迈出了第一步。我挑了难度不算高的 Codeforces Round 1109（Div. 3）进行 virtual participation，第一次完整感受限时读题、实现、提交和调试的节奏。

规定时间内，我只完成了 A、B 两题。C 的思路从一开始就走偏了：我试图模拟若干次交换，却没有把“哪些位置可以互相到达”看成连通性问题。可能也和当前进度有关，我还没有系统学到连通块与并查集。赛后看完题解，才知道这题最终可以落到 `gcd(x,y)` 划分的位置同余类上。我随后把判断改成了：

```cpp
string f(const vector<int>& arr, int x, int y){
    int g = gcd(x, y);
    for (int i = 0; i < (int)arr.size(); i++){
        if (arr[i] % g != (i + 1) % g)
            return "NO";
    }
    return "YES";
}
```

值 `arr[i]` 最终要回到第 `arr[i]` 个位置，只要当前位置 `i+1` 和目标位置模 `g` 不同，它就不可能通过距离为 `x` 或 `y` 的交换到达。代码并不长，真正缺的是比赛中把操作抽象成连通块的那一步。

D 在比赛末尾只来得及扫一眼，赛后再看时，排序翻转端点、把数组切成若干段，再让每一段独立选择正负的思路很快就明白了。以我现在掌握的排序和前缀和，它并没有超出我的能力范围；现场没做到它，主要还是因为 A、B 消耗了太多时间。

这点让我有些挫败。A、B 的思路都出来得很快，但代码实现时不够利落，频繁回头检查小问题，还保留了先存下全部测试数据、再统一处理之类不够适合比赛的写法。单看每一个问题都不严重，放进计时环境里却不断切碎时间，最后根本没有给后面的题留下完整的思考窗口。

第一次比赛只做出两题，和学了这么久数据结构与算法形成的心理预期有些落差。不过回头看，这次至少让我分清了两件事：会实现已经学过的数据结构，不等于能在陌生题面里迅速找到模型；赛后能够看懂 C、D，也不等于比赛现场已经具备发现它们的速度。
