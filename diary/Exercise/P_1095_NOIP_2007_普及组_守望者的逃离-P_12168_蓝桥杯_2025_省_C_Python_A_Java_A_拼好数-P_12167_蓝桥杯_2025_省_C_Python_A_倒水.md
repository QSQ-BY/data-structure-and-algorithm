## P1095：把跑步时间和技能时间拆开

[源码](../../Exercise/greedy_algorithm/P_1095_NOIP_2007_普及组_守望者的逃离.py)

守望者每秒可以跑 `17` 米，也可以花 `10` 点魔法闪烁 `60` 米，或者原地休息恢复 `4` 点魔法。我在文件里保留了递推和枚举两种写法，这里记录它们共同依赖的时间划分。

跑步不会改变魔法值，因此可以把一个方案里的跑步秒数移到末尾，同时保持所有闪烁、休息动作的相对顺序。总时间、总路程和魔法使用的合法性都不变。于是只需考虑前 `k` 秒专门闪烁或休息，其余时间全部跑步。

设 `magic[k]` 表示只使用闪烁和休息，经过 `k` 秒能走的最远距离。魔法足够就闪烁，否则休息；把已有条件下可以执行的闪烁提前，不会减少固定时间内能够完成的闪烁次数。

在 `test02()` 中，`mana` 和 `magic_distance` 沿着这个纯技能方案推进。下面摘录每次枚举后的计算部分，省略此前更新魔法和技能距离的分支：

```python
        # 计算在规定的 t 秒内，这种分配能走多远
        running_time = t - skill_time
        distance = magic_distance + running_time * 17
        farthest = max(farthest, distance)

        # 计算采用这种分配时，最少还要跑多少秒才能到达出口
        remaining_distance = max(0, s - magic_distance)
        need_running_time = (remaining_distance + 16) // 17

        total_time = skill_time + need_running_time
```

枚举从 `skill_time=0` 开始，覆盖完全靠跑步的情况。给定技能时间后，补齐剩余距离所需的跑步时间是向上取整的 `remaining_distance/17`；若总时间不超过 `t`，就能作为逃离时间的候选。若所有候选都超时，则输出 `farthest`。

另一种写法把这些枚举结果递推维护：

$$
best[i]=\max\bigl(best[i-1]+17,\ magic[i]\bigr).
$$

上一秒的最优方案再跑一秒，覆盖技能阶段在此前已经结束的选择；`magic[i]` 补上前 `i` 秒全部用于技能的选择。这里魔法值始终属于独立的纯技能方案，不能把它误认为 `best[i]` 对应方案剩余的魔法。两种思路都是 `O(t)` 时间，使用滚动变量时额外空间为 `O(1)`。

## P12168：先数 6，再处理最多三个数的组合

[源码](../../Exercise/greedy_algorithm/P_12168_蓝桥杯_2025_省_C_Python_A_Java_A_拼好数.py)

好数只要求十进制表示里至少出现六个 `6`，并不要求这些 `6` 连续。因此拼接顺序不会影响是否达标，我可以把每个原数替换成其中 `6` 的数量。

一个数本身含有至少六个 `6`，就单独组成一组；含零个 `6` 的数可以忽略，因为它占用组内名额却没有贡献。剩下只有 `1` 到 `5` 五类，源码用 `cnt` 统计数量。

“每组最多三个数”使得不同小数的作用不一样。比如贡献为 `1` 的数，即使有很多，也不能单独凑出一组达标组合；它要搭配 `5`，或者和另一个 `1` 一起搭配 `4`。

当前实现先用 `5` 搭配最小的可用贡献，处理完后，`4` 优先搭配两个 `1`：

```python
# 4：优先使用两个 1
k = min(cnt[4], cnt[1] // 2)
ans += k
cnt[4] -= k
cnt[1] -= 2 * k

# 然后考虑 4+2、4+3
for x in (2, 3):
    k = min(cnt[4], cnt[x])
    ans += k
    cnt[4] -= k
    cnt[x] -= k

ans += cnt[4] // 2  # 剩下的 4 两两组合
```

这里不能只追求当前组用的数最少。例如剩余贡献为 `4、2、2、2、1、1`，先选 `4+2` 后，余下的数无法再组成好数；选 `4+1+1`，就还能保留一组 `2+2+2`，总共两组。

处理到 `3` 时，源码先取 `3+2+1`，再取 `3+3`，最后尝试 `3+2+2`，余下的 `2` 则每三个一组。`3、3、2、2、1、1` 也能说明顺序的影响：先组成两个 `3+2+1` 可以得到两组，先把两个 `3` 配在一起就只剩一组。

我把这题留下，是为了记住压缩成计数之后仍要考虑小贡献能用在哪里。单纯让当前组合尽快达到六，可能提前消耗掉后面独立成组需要的数。设每个原数至多有 `L` 位，统计数位需要 `O(nL)` 时间，之后只操作固定数量的桶；当前源码仍保存了转换后的数组，所以总空间为 `O(n)`。

## P12167：只能向右倒水，限制来自每一个前缀

[源码](../../Exercise/binary_search/P_12167_蓝桥杯_2025_省_C_Python_A_倒水.py)

相同颜色的瓶子下标相差 `k`，不同颜色之间不能倒水，因此先按下标模 `k` 分组。每组内部还有限制：水只能从左边流向右边。

要让所有瓶子至少有 `x` 单位水，整组平均值够大只是必要条件。例如同组水量是 `[1,9]`，平均值为五，但右边不能补给左边，最小值仍然最多为一。

我在当前代码中检查每组的所有前缀。前 `count` 个瓶子至少需要 `count*x` 单位水，而它们无法从后面的瓶子得到补充：

```python
def check(x):
    # 判断能否让每个瓶子至少有 x 单位水
    for group in water:
        total = 0

        for count, number in enumerate(group, start=1):
            total += number

            # 当前前缀的水量不够，右边也无法给它补水
            if total < count * x:
                return False
    return True
```

这个条件也足够：从左往右处理，每个瓶子保留 `x`，把富余水量传给右侧。处理完前 `count` 个瓶子后，富余量就是 `total-count*x`。只要所有前缀都满足不等式，沿途就不会出现无法填补的缺口。

目标值越大，要求越严格，所以可以二分最大的可行值。源码把全体瓶子的平均值 `sum(arr)//n` 作为上界，使用向上取整的中点；可行时令 `left=mid`，否则令 `right=mid-1`。向上取整保证只剩两个候选值时仍能缩小范围。

一次检查会遍历全部瓶子，时间为 `O(n)`；设平均值上界为 `U`，整个实现为 `O(n log(U+1))`，分组存储占 `O(n)` 空间。

顺着这个条件还可以推出答案的直接表达式：

$$
\min_{\text{同色组 }g}\ \min_{1\leq c\leq |g|}
\left\lfloor\frac{\sum_{i=1}^{c}g_i}{c}\right\rfloor.
$$

每个前缀都给目标水位设了一个上限，取最小值即可。这是从当前判定条件推出的 `O(n)` 扫描思路，源码保留的仍是二分实现。以后复习这道题，我会先检查方向限制如何变成前缀约束，再看外层是否还需要二分。
