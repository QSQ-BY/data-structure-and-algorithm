## P6033 合并果子加强版：桶和队列一起取最小值

[源码](../../Exercise/greedy_algorithm/P_6033_NOIP_2004_提高组_合并果子_加强版.py)

每次取最小的两堆合并，是普通合并果子的做法。加强版把堆数放大到 $10^7$，但原始重量只有 $1$ 到 $10^5$。当前实现利用了这个值域：原始果堆用桶统计，合并出来的新果堆放到队列里。

桶指针 `p` 始终指向尚未取完的最小原始重量。原始果堆只会减少，所以它只向右移动，累计最多扫描整个值域一次。每次取最小值时，只需比较桶指针和队首：

```python
def get_min():
    global p

    # 找原始果堆中最小的
    while p <= MAXV and cnt[p] == 0:
        p += 1

    #原始果子中最小的
    x = p if p <= MAXV else INF

    # 找合并队列中最小的
    y = q[0] if q else INF

    if x <= y:
        cnt[p] -= 1
        return p
    else:
        return q.popleft()
```

队列为什么能一直有序，是这个写法需要说明的地方。假设本轮取出的两个最小值是 $a\le b$，新重量为 $a+b$。剩余元素都不小于 $b$，新加入的 $a+b$ 也不小于 $b$，所以下一轮取出的两个数都至少是 $b$，它们的和至少为 $2b\ge a+b$。后产生的合并重量不会变小，直接追加到队尾就可以。

这相当于合并两条有序的数据流：一条来自原始重量的桶，另一条来自新生成的重量队列。共进行 $n-1$ 次合并，每次调用两次 `get_min()`，总时间复杂度为 $O(n+V)$，其中 $V=10^5$。

当前 Python 程序仍然先把输入保存成 `fruits` 列表，再建立计数桶，队列也可能保存很多元素，所以总空间是 $O(n+V)$。算法减少了堆操作，但千万规模下的输入解析和 Python 对象占用仍需要单独考虑。本次重跑题面样例得到 `15`，没有据此认定最大数据已经通过。

## P3915 树的分解：向父节点交回多少余量

[源码](../../Exercise/backtrack_algorithm&search/P_3915_树的分解.py)

题目要求把树切成若干个大小都为 `k` 的连通块。总节点数能被 `k` 整除只是必要条件；树的形状也会限制怎样切边。

当前 DFS 返回的含义很具体：子树内部已经划走完整块以后，还必须与父节点连接的节点数。每个孩子只把剩余部分交上来，加上当前节点本身，正好达到 `k` 就切成一块，向父节点返回零。

```python
    def dfs(u, father):
        size = 1
        for v in graph[u]:
            if v == father:
                continue

            size += dfs(v, u)

        # 正好组成一个大小为 k 的连通块
        if size == k:
            return 0

        return size
```

对于不足 `k` 的剩余部分，树上只有经过父节点这一条路可以与外部连接，因此不能随意丢掉某个孩子的余量。恰好凑够 `k` 时也可以立即切开：它已经形成一个完整连通块，不再需要占用父节点。

如果余量超过 `k`，说明这些必须连在一起的节点已经无法装进一个块。源码没有在这里单独返回失败标记，而是继续把这个大于 `k` 的数向上传；父节点只会继续累加，它以后也不可能恰好等于 `k`，最终根节点的返回值就不会是零。这解释了当前实现为什么只检查 `remain == 0` 也能判断结果。

样例中的四节点链能分成两个二节点块，四节点星形树却不能：三个叶子都需要中心节点，无法同时满足。此次重跑输出依次为 `YES`、`NO`。DFS 时间复杂度为 $O(n)$，邻接表与递归栈占用 $O(n)$ 空间；链形树会产生线性递归深度。

## P2431 正妹吃月饼：枚举第一次小于上界的位置

[源码](../../Exercise/Ad-hoc/P_2431_正妹吃月饼.py)

每种月饼的重量依次为 $1,2,4,8,\ldots$，而且每种只有一个，所以选择月饼就是选择二进制位。总重量为 `x` 时，吃到的月饼数量恰好是 `x` 的二进制中 `1` 的个数。问题变成在 $[a,b]$ 内找二进制 `1` 最多的整数。

区间可能接近 $2^{63}$，不能逐个枚举。当前程序先考虑 `b` 本身，再枚举 `b` 中每一个为 `1` 的位置 `i`：保留更高位，把第 `i` 位变成 `0`，低位全部填成 `1`。源码构造的候选数等价于

$$
x=\left((b\mathbin{\gg}(i+1))\mathbin{\ll}(i+1)\right)\mathbin{|}(2^i-1).
$$

这个数一定小于 `b`，剩下只需检查 `x >= a`。满足下界就统计它的 `1`，更新答案。

这样枚举不会漏掉最优值。任意一个小于 `b` 的数，都有一个从高位向低位看的首次不同位置：`b` 在那里是 `1`，这个数在那里是 `0`。首次变小以后，所有低位都可以自由填写。把低位补满为 `1`，既不会超过 `b`，又会让数值和 `1` 的数量都不减少；如果原来的数在区间内，补满以后仍然满足下界。因此，每种首次变小的位置，只检查这个补满低位的候选就够了。

当前代码固定枚举 65 位，覆盖了题目的范围；若按位数 $L$ 分析，使用 `bin(x).count("1")` 的实现约为 $O(L^2)$。样例区间 `[16, 25]` 的输出是 `4`，例如 `23 = 10111₂`，可以选择重量为 `16`、`4`、`2`、`1` 的四个月饼。

## P2949 工作调度：先保留，超出容量再删掉最便宜的

[源码](../../Exercise/greedy_algorithm/P_2949_USACO_09_OPEN_Work_Scheduling_G.py)

每项工作耗时一个单位，只有在截止时间内完成才有收益。当前程序按截止时间排序，用小根堆保存暂时选中的收益：

```python
jobs.sort()
heap = []
heapq.heapify(heap)
for (time,value) in jobs:
    heapq.heappush(heap,value)
    while(len(heap) > time):
        heapq.heappop(heap)

print(sum(heap))
```

处理截止时间为 `time` 的任务时，当前考虑过的工作截止时间都不晚于它。前 `time` 个时间单位最多容纳 `time` 项工作，因此堆中任务数超过这个容量，就必须舍弃一项。删掉收益最小的任务，能在恢复容量约束时损失最少的收益。

更早的截止时间约束也不会被破坏。之前保留下来的任务已经能按时完成，新加入的任务截止时间最晚；若需要替换，删去任意旧任务都不会使旧任务的安排更困难。这样，小根堆维护的是可行的任务集合，不需要在处理每项工作时固定它最终放在哪个时间槽。

这题的截止时间能到 $10^9$，实际处理的对象却只有 $n$ 项任务。按任务排序并维护堆，就能把复杂度控制在 $O(n\log n)$，空间为 $O(n)$，无需扫描整条时间轴。此次重跑样例得到 `17`：截止时间为 `1` 的两项工作保留收益 `7` 的，再安排截止时间为 `2`、收益 `10` 的那项。
